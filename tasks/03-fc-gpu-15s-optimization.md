# Task: FC GPU 15 秒视频 1 分钟优化

## 目标

把 15 秒单人脸视频的端到端转换时间尽量压到 1 分钟内。

## 当前基线

- FC：8 vCPU / 32GB 内存 / 24GB GPU 显存 / `fc.gpu.ampere.1`
- 视频档位：`preview`
- 输出规格：360p / 12fps / quality 50
- 15 秒视频约 180 帧
- 1 分钟目标要求平均处理速度不低于 3 FPS
- 成本粗估：1 分钟约 ¥0.24，3-5 分钟约 ¥0.7-¥1.3，主要成本来自 FC GPU 运行时长

## 优化原则

先做低风险、可度量、对现有 App 影响小的优化；不要一开始做拆片并行。

## 简化任务拆分

### 01. 建立 15 秒视频 Benchmark

记录一次完整链路耗时：

- 冷启动
- 上传
- 服务端预处理
- 人脸检测
- 逐帧换脸
- 编码
- 下载
- 总耗时
- 粗估成本

验收：有一份可复测的 benchmark 结果，能看出最慢阶段。

### 02. 确认 CUDA 真正生效

检查真实视频 job 过程中是否使用 CUDA provider，避免 fallback 到 CPU。

验收：日志能证明 FaceFusion / ONNXRuntime 实际走 GPU。

### 03. Android 端极速压缩

上传前把视频压到接近服务端目标规格：

- 最长边 360px
- 12fps
- H.264 mp4
- 15 秒以内
- 合理码率，目标文件尽量 < 10-20MB

验收：服务端上传和预处理时间明显下降。

### 04. 服务端跳过重复预处理

如果输入已经满足 360p / 12fps / H.264，就不要再次转码。

验收：符合规格的视频直接进入检测/换脸阶段。

### 05. 降低冷启动影响

优先级：

1. 模型内置到镜像；
2. 容器启动时预热模型；
3. 必要时测试 FC 预留实例 / 最小实例数。

验收：热启动链路稳定；冷启动耗时有明确记录。

### 06. 推理与编码优化

在前面几项完成后再做：

- 源人脸只检测一次并缓存；
- 目标脸检测降频或跟踪；
- 只处理单主脸；
- 关闭增强类处理；
- 尝试 `h264_nvenc` 或更快编码 preset。

验收：15 秒视频处理 FPS 接近或超过 3 FPS。

### 07. OSS/网络路径优化

如果链路里使用 OSS：

- FC、OSS、ACR 尽量同地域；
- 优先使用内网 endpoint；
- 后续考虑 App 直传 OSS，FC 只收 object key；
- 结果回写 OSS，App 下载签名 URL。

验收：FC 不再被上传/下载大文件长时间占用。

## 暂不做

- 不先做多段切片并行；
- 不做大规模并发压测；
- 不改 Android 前端展示；
- 不开启 SLS；
- 不主动部署 dashboard/docs 站。

## 成功标准

- P0：15 秒视频端到端 ≤ 180 秒；
- P1：15 秒视频端到端 ≤ 90 秒；
- P2：15 秒视频端到端 ≤ 60 秒；
- 单次 60 秒成本控制在约 ¥0.24-¥0.27 量级；
- 输出质量保持 preview 可接受水平。
